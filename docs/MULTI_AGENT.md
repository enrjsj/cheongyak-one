# 청약한눈 단일·멀티 에이전트 사용법

## 기본 동작

**매번 단일/멀티를 지정할 필요가 없다.** AGENTS.md가 독립적인 작업에 서브에이전트를 사용하도록 요청하며 주 대화가 작업별로 판단한다. 이 판단은 모델의 계획 과정으로 수행된다. 모든 요청에 여러 에이전트를 띄우는 고정 스크립트는 아니다.

| 요청 특성 | 기본 선택 | 이유 |
| --- | --- | --- |
| 문구·CSS 한 곳 수정, 설명 요청 | single | 분배·취합 비용이 더 큼 |
| 같은 컴포넌트/메서드에 이어지는 수정 | single | 중복 쓰기와 순서 의존 |
| 계약이 정해진 API 구현 + 독립 화면 구현 | parallel | 소유 파일과 입출력 분리 가능 |
| 서로 다른 원인을 조사하는 복잡한 장애 | parallel 조사 → 총괄 수정 | 독립 가설을 빠르게 검토 |
| 인증/DB 등 중요한 변경의 독립 리뷰 | 구현 후 reviewer | 동일한 구현 판단을 다른 관점에서 확인 |

복잡하거나 파일이 많다는 이유만으로 분업하지 않는다. 선행 결과가 없으면 후속 구현을 기다린다. 분업 도구가 없거나 설정이 비활성화됐으면 이유를 보고하고 단일로 처리한다.

## 역할과 실제 설정

| 담당 | 역할 파일 | 책임 |
| --- | --- | --- |
| 총괄 | 주 대화의 AGENTS.md | 계획, 계약, 작업 배정, 패치 통합, 통합 검증, 사용자 보고 |
| 프런트 | `.codex/agents/cheongyak_frontend.toml` | 배정된 React 화면·상태·프런트 테스트 |
| 백엔드 | `.codex/agents/cheongyak_backend.toml` | 배정된 Spring API·업무 로직·DB 변경·백엔드 테스트 |
| 리뷰 | `.codex/agents/cheongyak_reviewer.toml` | 변경·기존 검증 증거를 읽고 오류/회귀/누락 보고 |

프로젝트 설정 `.codex/config.toml`:

```toml
[agents]
enabled = true
max_concurrent_threads_per_session = 3
```

현재 공식 설정에서 한도 3은 **주 에이전트를 제외한 하위 에이전트** 수다. 실제 사용은 필요한 인원만 하며 보통 총괄+작업자 1~2명으로 시작한다. 모든 역할을 매번 띄우지 않는다. 작업이 끝난 에이전트는 지원되는 종료 수단으로 정리하고, 없으면 더 이상 턴을 실행하지 않도록 둔다.

모델·추론 수준을 고정하지 않아 기존 사용자 선택을 상속한다. 사용자 프로필의 하위 에이전트 기본값이 있으면 그 설정도 영향을 줄 수 있다. 권한·네트워크·승인 정책은 완화하지 않는다. 리뷰 역할은 read-only 설정과 비수정 지침을 두지만 상위 런타임 정책/오버라이드가 최종 적용을 결정한다.

## 평소 요청 방법

기본 요청에는 기능만 적으면 된다.

> 청약 필터에서 공급기관 조건을 추가해줘. 기존 동작을 유지하고 테스트까지 진행해줘.

총괄은 먼저 다음과 같이 선택 이유를 알린다.

> API 계약을 먼저 확인한 후 프런트와 백엔드를 분리할 수 있어 멀티로 진행합니다. 공유 API 타입은 총괄이 관리합니다.

또는:

> 한 컴포넌트의 스타일 수정이라 단일로 진행합니다.

필요할 때만 자연어로 덮어쓴다. 아래 표현은 프로젝트 지침이며 별도의 Codex CLI 플래그/슬래시 명령이 아니다.

- `이번에는 단일 에이전트로 진행해줘.` → 위임하지 않는다.
- `프런트와 백엔드를 멀티 에이전트로 나눠줘.` → 가능한 독립 범위를 나누되 같은 파일은 동시 수정하지 않는다.
- `구현 후 다른 에이전트에게 리뷰받아줘.` → 구현을 마친 결과를 독립 검토한다.
- `앞으로 작업에 맞게 알아서 분업해줘.` → 기본 auto 정책과 같다.

코드 작성 요청에 분업 허용이 포함돼도 commit/push/PR/배포 권한까지 추가되지는 않는다. 기존 AGENTS.md의 별도 요청 규칙을 유지한다.

## 위임과 통합 절차

1. 총괄이 현재 Git 상태·기준 SHA·완료 기준·제외 범위를 확인한다.
2. API/데이터 계약, 각 작업의 입력·결과, 파일 소유자와 선행 작업을 정한다. 문서/분석만 필요하면 쓰기 권한을 부여하지 않는다.
3. 병렬 작성자는 각각 별도 Git worktree에서 작업한다. 같은 기준에서 생성하고 작업마다 정확한 경로를 전달한다. worktree는 부모의 미커밋 변경을 자동 포함하지 않으므로 필요한 최신 지침·계약·선행 변경만 snapshot/패치로 전달하고 실제 읽은 기준을 확인한다. 작업 중인 사용자 변경을 무조건 복사하지 않는다. worktree를 만들 수 없으면 쓰기를 직렬화한다.
4. 각 작업자에게 목표, 소유 파일, 수정 금지 파일, 관련 문서, 검증 명령, 결과 형식을 전달한다. 대화 전체나 비밀값을 복제하지 않는다.
5. 작업자는 작은 범위만 수정하고 해당 단위 테스트·브라우저 시나리오·백엔드 클래스만 검증한다. 각 작업자가 전체 Chromium·iPhone·하네스를 반복하지 않는다. 소유 범위 밖 변경이 필요하면 총괄에게 요청하고 기다린다. HANDOFF·작업 기록·공통 설정·Flyway 버전 배정은 총괄 소유다. 추가 에이전트를 만들거나 원격 반영하지 않는다.
6. 총괄은 완료된 작업의 실제 diff를 읽고 파일 소유권·기준을 확인한 뒤 통합한다. 작업자는 커밋 없이 patch를 제공할 수 있다. untracked 신규 파일도 패치에 포함됐는지 확인한다. blind copy, 강제 덮어쓰기, 자동 reset을 하지 않는다.
7. 공유 파일·API 계약 충돌은 총괄 한 명이 해결한다. 서로 다른 기준에서 나온 결과나 작성 중인 파일을 그대로 섞지 않는다.
8. 쓰기가 멈춘 통합본을 reviewer가 읽는다. reviewer는 빌드/테스트로 파일을 쓰지 않고 기존 결과를 읽으며, 빠진 검증은 총괄에 요청한다.
9. 총괄이 수정·기록을 모아 파일을 고정한 뒤 최종 전체 검증을 한 차례 수행한다. 앱 변경은 `harness.mjs verify --base <기준SHA> --scope full`, UI/모바일·인증은 `--extended`, PostgreSQL은 별도 경로를 사용한다. 문서만 바뀌었다면 docs 범위를 사용한다. 실패는 관련 검사부터 수정·재검증한 뒤 필요한 통합 검증을 수행한다. 새 코드에 이전 결과를 재사용하지 않으며, 결과 기록만 추가된 경우의 처리와 CI 기준은 `docs/HARNESS.md` 3·7절을 따른다. 결과·미검증은 HANDOFF에 남긴다.

**테스트 실행 주의:** worktree는 포트를 격리하지 않는다. 기존 브라우저 테스트는 4173, 실제 인증 테스트는 4180/8081을 쓴다. 포트를 사용하는 검증은 총괄이 직렬 실행하거나 이미 검증된 포트 분리 설정을 배정한다. 여러 작업자가 기본 E2E 또는 full 검증을 동시에 실행하지 않는다.

자식 작업 실패 시 다른 작업을 무한 재시도시키지 않는다. 실패한 범위와 재현 근거를 받은 뒤 범위를 줄이거나 총괄이 이어받는다. 작업 중단을 요청받으면 실행 중인 자식도 중단하고 미완료 산출물을 완료로 취급하지 않는다. worktree는 변경을 확인하기 전 삭제하지 않는다.

### 작업자 결과 형식

```text
담당/목표:
기준 SHA / 작업공간:
수정 파일과 이유:
실행한 검증 / 결과 / 증거:
미검증 및 막힌 지점:
공유 파일 또는 계약에 필요한 후속 변경:
통합할 패치 위치 또는 변경 목록:
Git/배포: 실행하지 않음
```

이 절차는 AGENTS 및 역할 지침으로 운영된다. 파일 소유권이나 토큰 한도를 OS 수준에서 강제하는 별도 실행기가 아니다.

## 로컬 Codex에서 적용 확인

1. 이 변경이 들어 있는 프로젝트를 로컬 Codex에서 연다. GitHub main에 반영되기 전에는 로컬 변경/패치를 먼저 적용해야 한다.
2. 사용하는 클라이언트가 프로젝트 `.codex/config.toml`과 standalone `.codex/agents/*.toml` 형식을 지원하는 버전인지 확인한다. 이 가이드는 2026-10-07 공식 문서 기준이다. 이전 버전에 설정 키를 억지로 추가하지 말고 해당 버전의 문서를 확인한다.
3. 프로젝트 설정은 신뢰된 프로젝트에서 읽힌다. 사용자가 프로젝트 내용을 확인한 후 정상적인 신뢰 절차를 거친다. 글로벌 설정이나 관리 정책을 우회하지 않는다.
4. 설정 반영을 위해 새 작업/세션을 시작하고 아래처럼 **읽기 전용**으로 점검한다.

> 적용된 AGENTS.md와 프로젝트 에이전트 설정을 확인해줘. 프런트 진입점과 백엔드 진입점을 서로 다른 에이전트에게 읽기 전용으로 조사하게 하고, 실제 생성한 에이전트·각 결과·설정 적용 여부를 보고해줘. 파일 수정이나 커밋은 하지 마.

5. 실제 하위 스레드 생성과 결과 수신을 확인한다. 이름만 역할별로 나눈 답변은 분업 실행 증거가 아니다. 지원 버전/활성 정책 때문에 분업이 불가능하면 그 상태를 그대로 보고한다.

`node scripts/harness.mjs verify`는 테스트를 실행하며 에이전트를 생성하지 않는다. TOML 구문 검사도 Codex가 역할을 실제로 불러왔다는 검증이 아니다. CLI 설치 여부와 지원 버전은 실행 환경별로 확인하고, 사용자 PC의 역할 로딩/동시 한도 적용은 해당 PC의 새 세션에서 별도로 확인한다.

현재 하네스는 `.codex/*.toml`을 공통 설정으로 취급해 auto 검증 범위를 full로 선택한다. 설정·문서만 바꾼 이번 작업에서 `--scope docs`로 자체 테스트를 실행한 것은 명시적으로 좁힌 검증이며 앱 전체/로컬 Codex 로딩 통과를 뜻하지 않는다.

## ChatGPT Work와 비용

이 채팅의 호스팅 서브에이전트 기능과 사용자 PC의 로컬 Codex 설정은 별개다. Work에서 실제 분업을 실행할 수 있어도 로컬 역할 TOML이 자동 로드됐다고 주장하지 않는다. 호스팅 런타임에서는 사용할 수 있는 분업 도구와 지침으로 같은 역할을 배정한다.

서브에이전트마다 모델·도구 작업이 발생하므로 일반적으로 토큰 사용량이 증가한다. 이 설정은 신규 API 키나 별도 유료 서버를 만들지 않으며, 실제 사용량은 사용 중인 Codex/ChatGPT 이용 방식에 따른다. 비용을 줄이기 위해 좁은 과제, 필요한 문서만 전달, 최대 3명, 재귀 분업 금지, 중복 전체 테스트 방지를 기본으로 한다.

이는 요청을 처리하는 동안의 자동 판단이다. 사용자가 자리를 비웠을 때 주기적으로 작업을 시작하는 스케줄러나 상시 실행 서비스는 추가하지 않는다.
